## 2026-08-22 — draw.io 다이어그램 도구 (브랜치 `feat/drawio-embed`)

### 왜

mermaid는 문법을 글로 써야 한다. 사용자가 원한 것은 **마우스로 끌어다 놓고 선이 알아서
달라붙는** 편집이라 방식 자체가 맞지 않았다.

편집기를 직접 만드는 안은 접었다. 드래그·연결점 스냅·선 경로·선택·되돌리기를 전부
구현해야 하고, 다 만들어도 draw.io보다 못하다. **draw.io 공식 임베드**를 쓰기로 했다
(사용자 결정). 우리가 만든 것은 바깥 틀과 내보내기뿐이다.

### 확인하고 시작한 것

`embed.diagrams.net`이 `X-Frame-Options`도 `frame-ancestors`도 보내지 않는다(HTTP 200).
우리 도메인에서 iframe으로 열린다는 것을 먼저 확인하고 설계했다. Apache 2.0, 계정 불필요,
통신은 전부 클라이언트 쪽.

### 설계에서 지킨 것

**주소와 origin이 한 값에서 나온다**(`drawio.py`). 이게 갈라지면 편집기는 멀쩡히 뜨고
그림도 그려지는데 **버튼만 아무 반응이 없다** — postMessage가 origin 검사에서 전부
버려지기 때문이다. 화면만 봐서는 원인을 알 길이 없어서, 파이썬이 두 값을 함께 내보내고
테스트가 둘의 일치를 지킨다.

**내보내기는 한 번에 하나 + 20초 타임아웃.** 응답이 한 번 유실됐을 때 잠금이 안 풀리면
버튼 다섯이 영원히 죽고, 콘솔에도 아무것도 안 남는다. 이 화면에서 가장 잡기 어려운
실패라 처음부터 막았다.

**`dark=0` 고정.** OS가 다크면 편집기가 검게 뜨고 내보낸 그림의 글자가 흰색이 된다.
흰 배경 블로그에 올리면 그림은 나오는데 글자만 안 보인다.

**자동 저장 실패를 삼키지 않는다.** mermaid 원고는 몇 KB지만 draw.io XML은 그림 안에
이미지가 들어가면 MB 단위가 되어 localStorage 한도를 실제로 넘는다. `catch {}`로 두면
사용자는 저장되는 줄 알다가 새로고침에서 통째로 잃는다 → 한 번 경고하고 저장을 멈춘다.

### 인라인 조각 — 이 도구의 실제 알맹이

'복사' 버튼이 내놓는 조각은 Blogger의 HTML 보기에 **직접** 붙여넣는 것이라 우리 변환기를
지나지 않는다. 그래서 변환기가 해 주던 일을 JS가 미리 해야 한다.

1. **`<div>`로 감싼다.** 마크다운 원문에 최상위 `<svg>`를 넣으면 Python-Markdown이 인라인
   raw HTML로 보고 **안쪽 글자에까지 마크다운 문법을 적용한다** — `<text>*별*</text>`가
   `<em>`이 된다. `<div>`로 감싸면 블록 raw HTML로 통째 보존된다.
2. **개행을 없앤다.** Blogger의 '엔터 = 줄바꿈'이 개행을 전부 `<br>`로 바꾼다.
3. **id에 접두사를 붙인다.** draw.io SVG는 화살표 머리·그라디언트를 `<defs>`의 id로
   참조한다. 한 글에 그림을 둘 넣으면 **두 번째가 첫 번째의 정의를 먹어** 화살표가
   사라지거나 색이 바뀐다. 오류가 안 나서 눈으로만 보이는 고장이다.
4. `xmlsvg`가 아니라 `svg`로 뽑는다 — `content` 속성에 든 원본 XML의 이스케이프가
   우리 변환기를 지나며 풀려 버리고, 길이도 두 배가 된다. 다시 편집할 원본은 파일
   저장 쪽이 맡는다.

### 곁다리로 고친 것 — 역방향이 그림을 삼키고 있었다

`to_markdown`이 인라인 SVG의 태그를 전부 벗겨 텍스트만 남기고 있었다. `raw_html_kept`도
0이라 **경고조차 없었다.** 표에는 적용된 원칙("되돌릴 수 없는 것은 HTML로 남기고 경고")이
그림에는 빠져 있던 것이다. 이 도구가 조각을 내보내기 시작하면 바로 밟는 길이라 함께 고쳤다.

고치면서 밟은 함정: 처음에 "svg를 품은 div는 보존"으로 썼더니 **글 전체를 감싼 컨테이너
div도 그림을 품고 있어서** 본문이 통째로 원본 HTML로 남았다. 왕복 테스트가 잡았다.
직계 자식만 보도록(`_wraps_svg`) 좁혀서 해결했다.

### 검증한 것 / 못 한 것

- 테스트 123개 통과(14개 추가). 새로 넣은 것 중 값이 큰 둘:
  **임베드 설정 테스트**(`embed=1`·`proto=json`·`dark=0`·origin 일치)와
  **화면 배선 테스트**(JS가 `getElementById`로 찾는 id가 실제 화면에 있는가 — 두 도구
  화면 모두). 둘 다 어긋나면 조용히 죽는 종류라 눈으로는 못 잡는다.
- 조각 변환 로직(`toFragment`)을 실제 draw.io 형태의 SVG로 node에서 돌려 확인했다 —
  XML 선언·DOCTYPE·주석 제거, 개행 0, id 접두사와 `url(#…)` 참조가 함께 바뀌는지,
  두 번 뽑으면 id가 서로 다른지.
- 그 조각을 **우리 변환기에 통과시켜** 끝까지 확인했다: `<em>` 오염 없음, 개행 없음,
  역방향에서 보존 + 경고, 왕복 안정.
- **화면을 실제로 눌러 보지는 못했다.** 이 세션의 Chrome이 로컬 서버에
  `ERR_CONNECTION_REFUSED`를 낸다(인터넷은 되는데 우리 `127.0.0.1`만 못 본다).
  mermaid 때와 같은 벽이다. 배포본에서 사람이 봐야 한다.

### 남은 일 · 주의점

- 배포본 확인 목록: 편집기가 뜨는지 · 도형을 끌면 선이 달라붙는지 · 내보내기 4종이
  파일을 떨구는지 · 인라인 조각이 클립보드에 오는지 · 새로고침해도 그림이 남는지 ·
  저장한 SVG를 다시 불러오면 이어서 편집되는지.
- **가장 불확실한 지점: 인라인 조각을 Blogger에 실제로 붙여넣었을 때 살아남는가.**
  Blogger 편집기가 HTML을 다시 직렬화하면서 `viewBox`·`foreignObject`의 대소문자를
  못 살릴 가능성이 있다. 계정 접근이 필요해 이번에도 확인이 안 된다.
  조각에 `foreignObject`가 있으면 화면이 미리 경고하도록 해 뒀다.
- `diagram.js`는 `shared.js`를 아직 안 쓴다(같은 함수가 두 벌 있다). mermaid 화면을
  사람이 확인하기 전에는 건드리지 않기로 했다 — 확인할 것이 두 배가 된다.

## 2026-08-20 — Mermaid 다이어그램 도구 (브랜치 `feat/mermaid-editor`)

### 왜

탭에 '준비 중'으로 자리만 있던 두 번째 도구. 확인해 보니 **변환 쪽은 이미 다 돼 있었다** —
`pipeline.py`가 ```` ```mermaid ````를 빼돌려 `<div class="mermaid">`로 내보내고, 개행을
`&#10;`로 살리고, `to_markdown.py`가 되돌리고, 미리보기 iframe에는 테마 스니펫이 들어가
그림까지 나온다. **없던 것은 다이어그램을 그리는 화면 하나뿐이었다.**

사용자 결정: 텍스트 편집 + 실시간 미리보기 + 템플릿 갤러리. 결과물은 코드블록·SVG·PNG 셋.
GUI 노드 편집기는 범위 밖으로 뒀다(mermaid가 GUI 편집을 지원하지 않아 캔버스 엔진을
직접 만들어야 하고, 이 저장소 규모를 크게 넘는다).
'변환 탭으로 바로 보내기'는 값이 적다고 판단해 빼기로 합의했다 — 실제 흐름은 다이어그램을
**글 원문 안에** 붙여넣고 글 전체를 변환하는 것이라, 다이어그램만 따로 변환할 일이 드물다.

### 설계에서 지킨 것

**이 화면에는 API가 없다.** mermaid는 브라우저에서 그리는 라이브러리이고, 브라우저에서
그려야 Blogger에 붙여넣었을 때와 같은 그림이 나온다(Blogger 쪽도 테마 스니펫의 같은
mermaid가 같은 소스를 그린다). 배포처가 Vercel Python 함수라 서버에서 Node를 돌릴 수도 없다.
→ 변환 화면의 "변환은 전부 서버가 한다"와 반대인데, **이유가 같다**: 사용자가 화면에서
보는 것이 실제 결과와 같아야 한다.

**mermaid 버전은 `converter/snippet.py`가 단일 출처.** `MERMAID_SRC`·`MERMAID_THEME`를
상수로 빼고 테마 스니펫과 편집기가 같은 값을 쓴다. 갈라지면 편집기에서 본 그림과 Blogger의
그림이 달라진다. `THEME_SNIPPET` 출력 문자열은 **한 글자도 바뀌지 않았다**(해시로 확인).

**템플릿 데이터는 `converter/`에 두지 않았다.** 그 폴더는 블로그가 복사해 가는 변환 코어다.
편집기 UI 데이터는 루트 `diagrams.py`에 뒀다 — `tools.py`와 같은 방식.

### 실제 글이 아니라 **실제 브라우저**에서 잡은 것 — 또 렌더에서 나왔다

로컬 서버에 브라우저가 닿지 않아(아래 참고), mermaid를 CDN에서 직접 불러 **템플릿 5종과
내보내기 코드 경로를 그대로 돌려 봤다.** 테스트가 전부 통과하는 상태에서 두 건이 나왔다.

1. **내보내기(SVG·PNG)가 전부 실패하고 있었다.**
   SVG 여는 태그 앞에 크기를 끼워 넣었는데, mermaid는 이미 `width`와
   `style="max-width:…"`를 달아서 내놓는다. 속성이 두 번 나오면 SVG는 XML이라
   `Attribute width redefined`로 **파일 전체가 무효**가 되고 브라우저가 그림을 못 읽는다.
   증상이 "저장 버튼을 눌러도 아무 일이 없다"라서 코드만 봐서는 안 보인다.
   → 여는 태그의 `width`/`height`/`style`을 **지우고 다시 넣는다**(`standalone()`).

2. **ER 템플릿이 파싱 자체를 못 했다.**
   `CATEGORY ||--o{ POST : 담는다`처럼 관계 라벨을 맨몸으로 두면
   `Parse error on line 2`가 난다. 따옴표로 감싸면(`: "담는다"`) 정상이다.
   불러오자마자 안 그려지는 템플릿은 출발점이 되지 못하므로 이건 치명적이었다.

부수적으로 확인한 것: 플로우차트·클래스 다이어그램의 SVG에는 `<foreignObject>`가 들어간다
(시퀀스·간트·ER에는 없다). `htmlLabels:false`로 그리면 사라지고 `<text>` 10개가 대신 생긴다 —
PNG 경로를 따로 둔 근거다.

### 남은 일 · 주의점

- **화면을 실제로 눌러 보지 못했다.** 이 세션의 Chrome은 인터넷은 되는데
  `127.0.0.1:5001`에 `ERR_CONNECTION_REFUSED`가 난다(샌드박스 밖에서 서버를 다시 띄워도
  같다 — 브라우저가 다른 네트워크에 있는 것으로 보인다). 지난 세션과 같은 벽이다.
  대신 ① 템플릿·내보내기 로직을 브라우저에서 직접 검증하고 ② 페이지 HTML의 `id`와
  `diagram.js`가 찾는 `id`가 전부 맞는지 정적으로 대조했다. **버튼 클릭·복사·다운로드가
  실제로 도는지는 사람이 봐야 한다.**
- PNG 래스터 결과의 픽셀까지는 못 쟀다. 스크립트를 두 번 돌리자 렌더러가 멎어
  (CDP 45초 시간 초과) 같은 방식 반복을 그만뒀다.
- 미리보기 배경 칩은 **배경만 바꾼다.** 다이어그램 테마는 `neutral` 고정이라, 검은 배경
  Blogger 테마에서는 글자가 어둡게 남는다. 사용자의 Blogger 테마가 검은 배경이므로
  실제로 읽히는지는 배포본에서 확인이 필요하다 — 안 읽히면 다이어그램 테마를 팔레트처럼
  고를 수 있게 하는 것이 다음 수다.
- `docs/WORKLOG.md`에 **0.6.0~0.6.3(도구 탭·sane_lists·Vercel 배포·푸터) 항목이 없다.**
  CHANGELOG에는 있다. 그 작업을 한 세션이 남기지 않은 것이라 여기서 지어내지 않았다.

## 2026-08-15 — 역방향 HTML → 마크다운 (브랜치 `feat/html-to-markdown`)

### 왜

정방향만으로는 한 방향 통행이다. Blogger에만 있는 글을 블로그로 되찾아올 수 없고,
정방향이 제대로 동작했는지 **왕복으로 검증**할 수도 없다.

사용자가 입력 출처 셋(우리 출력·Blogger 글·임의 웹페이지)을 모두 다루기로 했고,
bs4 추가를 승인했다.

### 설계에서 지킨 것

**`converter/__init__.py`에서 bs4를 import하지 않는다.** 블로그가 이 폴더를 복사해
쓰는데 그쪽은 정방향만 쓴다. `__init__`이 끌어오면 블로그에 없는 의존성이 강제된다.
`from converter.to_markdown import to_markdown`으로 직접 import한다. `app.py`·`cli.py`도
역방향 경로 안에서 늦게 import한다.

**되돌릴 수 없는 것은 버리지 않는다.** 셀 병합 표·중첩 표·iframe은 마크다운에 문법이
없다. 억지로 평평하게 만들면 표가 조용히 뭉개지므로 원본 HTML을 그대로 남기고 경고한다.

### 실제 글에서 잡은 것 — 또 렌더에서 나왔다

1. **본문의 대괄호가 수식으로 둔갑했다.**
   처음에는 마크다운 기호를 전부 이스케이프했다. 그랬더니 본문의
   `[이미지2 - 년도 별 단속 횟수]`가 `\[…\]`가 되고, **다시 변환할 때 arithmatex가
   그걸 LaTeX display 수식 구분자로 읽어 문단 하나가 통째로 수식이 됐다.**
   이스케이프가 없던 문법을 만들어 낸 것이다.
   → "그 자리에서 실제로 문법이 될 수 있을 때만" 이스케이프하도록 바꿨다.
   `2 * 3`은 그대로, `_밑줄_`만; 링크가 될 수 있는 대괄호만; 태그로 보이는 꺾쇠만;
   줄 맨 앞의 `#`·`>`·목록 기호만.

2. **정방향이 코드블록 언어를 버리고 있었다.**
   `<pre><code>`에 `class="language-x"`가 없어 왕복하면 ```` ```python ````이
   ```` ``` ````으로 무너졌다. 정방향에 클래스를 되살렸다. 색은 이미 칠해져 있어
   화면에는 영향이 없고, 블로그의 highlight.js도 같은 클래스를 읽는다.

3. **중첩 목록은 4칸이어야 한다.**
   Python-Markdown 3.4.1은 CommonMark가 아니라 원조 Markdown.pl 규칙을 따라 4칸부터
   중첩으로 본다. 요즘 흔한 2칸으로 내보냈더니 되돌린 글을 다시 변환할 때 중첩이
   조용히 평평해졌다.

4. **loose/tight 목록.** 항목 사이 빈 줄 유무가 `<li>`의 `<p>` 감싸기를 바꾼다.
   원본이 어느 쪽이었는지 보고 따라가지 않으면 왕복에서 항목 간격이 달라진다.
   `<li>`에 직계 `<p>`가 있으면 loose였다는 신호다.

### 테스트 전략

글자까지 같기를 요구하지 않는다. **다시 변환했을 때 같은 HTML이 나오면 된다**
(`StabilityTest`). 표기가 달라도 렌더가 같으면 정보가 새지 않은 것이다.

실제 글(21KB) 왕복: 렌더에 영향 없는 공백(문단 끝 여백)만 빼면 HTML이 동일하다.

### 발견했지만 고치지 않은 것

**불릿 목록 바로 뒤에 번호 목록이 오면 두 번째가 첫 번째에 흡수된다.**
`1. 2.`가 불릿이 되고, 반대 순서도 마찬가지다. 사이에 문단이 있으면 정상이다.
Python-Markdown 3.4.1의 동작이라 **블로그에도 같은 문제가 있다.**
`sane_lists` 확장이 고치지만 넣으면 블로그와 출력이 갈라진다 — 이 저장소의 전제가
"블로그와 같은 모양"이므로 혼자 결정하지 않고 남겨 뒀다.

### 남은 일

- **역방향 화면을 실제로 눌러 확인하지 못했다.** Claude in Chrome 확장이 localhost에
  접근하지 못해 API·JS 문법·테스트만 검증했다. 헤드리스 Chrome으로는 클릭을 못 한다.

## 2026-08-12 (3) — `<style>` 블록 출력 모드 (브랜치 `feat/theme-palette`)

### 전제가 틀렸다

사용자가 "Blogger 글에 CSS 넣으면 적용 안 되겠지?"라고 물었고, 확인해보니
**된다.** 글 본문의 `<style>` 태그는 정상 처리된다. `<html>`/`<head>`/`<body>`만
넣지 않으면 된다(이미 페이지가 감싸고 있으므로).

나는 그때까지 "글 본문에 CSS를 넣을 수 없다"를 설계의 대전제로 삼고 있었다.
전제가 틀렸으니 선택지가 하나 늘었다.

### 다만 다크 문제는 이걸로 안 풀린다

기대할 만한 건 `prefers-color-scheme`인데, 그건 **OS/브라우저 설정**을 따르지
Blogger 테마 밝기를 따르지 않는다. 테마가 OS와 무관하게 늘 검은색이면 밝은 OS에서
여전히 라이트 색이 나온다. **팔레트 선택은 그대로 필요하다.**

### 그래서 실익은 조판 정확도다

인라인 모드는 blog.css의 `> * + *`(형제 여백)와 `li + li`를 표현할 수 없어 px로
어림잡고 있었다. `<style>` 모드는 이걸 **그대로** 옮긴다. 길이 감소는 부수 효과다.

**손익분기를 실측했다 — 원문 약 700자.** 그보다 짧으면 스타일시트 고정 비용(~6.6천 자)
때문에 CSS 모드가 오히려 길다. "CSS가 항상 짧다"고 안내하면 안 된다.

| 원문 | 인라인 | CSS |
|---|---|---|
| 264자 | 2,609 | 6,931 |
| 880자 | 8,192 | **7,838** |
| 1,760자 | 16,172 | **9,138** |
| 실제 글 21KB | 43,637 | **24,633** |

### 잡은 버그 셋 (전부 렌더/적대적 테스트로 발견)

1. **글자색을 컨테이너 상속에 맡긴 것.**
   `.md2b{color:…}` 하나 두고 `p`·`td`는 상속받게 뒀는데, **상속은 요소를 직접
   겨냥한 규칙에 무조건 진다.** 특이도 문제가 아니다 — 테마에 `p{color:#888}` 한
   줄만 있으면 그게 이긴다. 적대적 테마 CSS를 일부러 주입해 렌더해보고 발견했다.
   → 글자를 담는 요소마다 `color`·`font-family:inherit`를 명시.

2. **Pygments `get_style_defs(scope)`가 스코프 밖 규칙을 흘린다.**
   넘긴 선택자와 무관하게 `pre { line-height: 125% }`와 줄번호 규칙 넷을 함께 뱉는다.
   앞의 것은 **테마의 모든 코드블록 행간을 건드린다.** → 토큰 규칙만 남기고 거름.

3. **다크 팔레트의 코드 배경이 라이트 값으로 덮였다.**
   같은 `get_style_defs`가 끼워 넣는 `{scope}{background:…}`는 Pygments Style
   클래스에 박제된 값(`BlogDarkDimmed.background_color` = 라이트 `#11162A`)이다.
   내 규칙 뒤에 놓이면서 다크의 `#0A0F1A`를 덮었다. → 2번과 같이 걸러냄.

### 스코프 규칙

- 루트 클래스 `md2b md2b-<팔레트>`. 팔레트를 클래스에 넣은 이유는 **글 목록·홈에서
  여러 글의 style 블록이 동시에 로드**되기 때문이다. 팔레트가 다른 두 글이 같은
  페이지에 있어도 서로 덮어쓰지 않는다.
- 선택자는 클래스를 겹쳐 쓴다(`.md2b.md2b-dark`) — 특이도 (0,2,x)로 테마 규칙을 이긴다.
  `!important`를 뿌리는 것보다 낫다. 사용자가 나중에 직접 붙일 여지를 남긴다.
- **테스트가 스코프를 강제한다** (`test_every_rule_is_scoped`). 규칙을 추가할 때
  스코프를 빠뜨리면 테스트가 잡는다.

### CSS도 개행을 남기지 않는다

Blogger의 줄바꿈 자동 변환은 `<style>` 안이라고 봐주지 않는다. `<br>`이 끼면
그 지점부터 CSS가 깨진다. 스타일시트도 한 줄로 낸다.

## 2026-08-12 (2) — 팔레트 (브랜치 `feat/theme-palette`)

### 무엇이 문제였나

사용자가 변환 결과를 실제 Blogger에 붙여넣었더니 **색이 애매하다**고 했다.
원인은 명확했다 — 사용자의 Blogger 테마가 **검은 배경**인데, 나는 blog.css의
**라이트** 토큰만 인라인으로 박아뒀다. 본문 `#1A1F2B`, 제목 `#0D1220`이 검은 배경에
그대로 얹히니 글자가 배경에 묻힌다.

### 왜 자동 대응이 안 되나 (중요)

**인라인 스타일에는 미디어쿼리를 넣을 수 없다.** `prefers-color-scheme`으로
자동 전환하려면 `<style>` 블록이 필요한데, 그건 이 도구의 전제(글 본문에 CSS를 넣을
수 없다)와 정면으로 충돌한다. 그래서 자동 해결책이 없고, **선택지를 주는 것**이
유일한 답이었다.

### 팔레트 3종

| 이름 | 출처 | 대가 |
|---|---|---|
| `light` | blog.css 라이트 토큰 | 검은 테마에서 본문이 묻힌다 |
| `dark` | blog.css `html[data-theme="dark"] body.blog` (98행~) 값 그대로 | 테마를 밝게 바꾸면 기존 글이 안 읽힌다 |
| `inherit` | 색을 지정하지 않음 | 어떤 테마에도 맞지만 블로그와 색이 다르다 |

`inherit`은 `text`/`heading`/`text_muted`를 `None`으로 두고, `_color()` 헬퍼가
선언 자체를 빼버린다. 강조색은 `currentColor`, 선·배경은 밝기 양쪽에서 읽히는
중립 회색(`rgba(128,128,128,...)`)을 쓴다.

**코드블록은 팔레트를 타지 않는다.** 블로그도 두 테마 모두 어둡게 둔다
(`blog.css:435` 주석). 배경만 팔레트를 따른다(`light` `#11162A` / `dark` `#0A0F1A`).

### 구조 변경

`theme.py`의 모듈 상수를 함수로 바꿨다.

- `TAG_STYLES` → `tag_styles(palette)`
- `WRAPPER` → `wrapper(palette)`
- `PRE_STYLE` → `pre_style(palette)`

`_Inliner`도 `theme.TAG_STYLES`를 직접 읽지 않고 생성자로 주입받는다.
`highlight.py`의 `BlogDarkDimmed.background_color`는 `nowrap=True`라 출력에
나가지 않지만 Pygments가 요구하는 필드라 라이트 값을 대표로 남겼다.

### 확인한 것

- 테스트 33개 통과 (팔레트 7개 추가)
- 실제 글을 다크 팔레트로 렌더해 헤드리스 Chrome으로 확인 — 본문·표·코드블록·
  인용구·링크 모두 검은 배경에서 읽힌다
- `inherit`도 어두운 배경 시뮬레이션에서 확인 — 링크가 `currentColor`라
  파란색 대신 본문색+밑줄로 나온다(의도한 대가)

### 남은 일

- 사용자의 실제 Blogger 테마에서 다크 팔레트 최종 확인 (아직 못 함)
- 테마를 바꿀 계획이 있는지에 따라 `dark`와 `inherit` 중 어느 쪽을 기본으로 쓸지 결정

## 2026-08-12 — 첫 구현 (브랜치 `feat/blogger-converter`)

### 무엇을 왜 했나

블로그(`blog.devprofessional.xyz`, 레포 `django_blog_Enhanced`)에 쓰던 마크다운 원문을
Blogger에도 올리고 싶은데, **Blogger는 마크다운을 지원하지 않는다**. 그대로 붙여넣으면
`#`이 글자로 찍힌다. 그래서 HTML로 변환하는 도구를 만들었다.

우회로도 검토했다. Blogger 테마에 `marked.js`를 심으면 마크다운 원문을 그대로 붙여넣을 수
있지만, **크롤러·RSS 피드에는 마크다운 원문이 그대로 노출**된다(SEO 손해). 브라우저 확장이나
StackEdit 퍼블리시는 유지보수가 끊긴 서드파티에 블로그 권한을 넘겨야 한다.
→ **정적 HTML 변환**이 유일하게 SEO·피드·아카이빙이 안전한 선택이었다.

### 사전 조사에서 확인한 것 (중요)

블로그 레포를 뜯어서 확인한 사실들이다. 이걸 모르면 결과물이 블로그와 다르게 나온다.

| 버전 고정 이유 | `requirements.txt` 주석 | `markdown==3.4.1` + `pymdown-extensions==9.11`. 올리면 블로그 빌드가 깨짐 |

> `body.blog .article-body` 블록을 봐야 한다.

### 설계 결정과 근거

1. **`converter/`는 프레임워크를 import하지 않는다.**
   나중에 블로그(Django)에 붙일 때 폴더째 복사하고 뷰에서 `convert()`만 부르면 되게 하려는
   의도적 제약이다. Flask는 `app.py`에만 있다.

2. **codehilite를 뺐다.** codehilite는 CSS 클래스를 뱉는데 Blogger에는 그 CSS를 넣을 데가
   없다. 대신 변환 후 단계에서 Pygments로 직접 칠하고 `noclasses=True`로 색을 span에 박는다.
   블로그도 실제 색은 브라우저의 highlight.js가 칠하므로, 뒤 단계에서 칠하는 쪽이 오히려
   블로그 동작에 가깝다.

3. **개행을 한 글자도 남기지 않는다.** Blogger의 '엔터 = 줄바꿈' 설정이 켜져 있으면 붙여넣은
   HTML의 개행이 전부 `<br>`이 된다. 설정을 끄라고 안내하는 것보다, 설정과 무관하게 같은
   결과가 나오게 만드는 편이 안전하다.
   - 코드블록 줄바꿈 → `<br>` (`<pre>` 안에서 정상 렌더)
   - 다이어그램 줄바꿈 → `&#10;` (아래 함정 참고)
   - 그 외 → 공백 하나로 접음

4. **인라인화는 `html.parser`로 한다.** BeautifulSoup을 새로 들이지 않았다. 입력이 우리가
   만든 HTML이라 파서 견고성이 크게 필요하지 않다. `convert_charrefs=False`가 **필수**다 —
   기본값(True)이면 `&lt;`가 문자로 풀려 코드블록의 `<`가 다시 태그로 해석된다.

### 실제 문서로 테스트하다 잡은 버그 2개

테스트는 26개 전부 통과했는데도, 실제 글(수원시 주차 문제 분석, 21KB)을 브라우저에 띄우니
바로 두 개가 보였다. **단위 테스트만으로는 못 잡는 종류였다.**

1. **코드블록에 `&quot;`가 글자 그대로 찍혔다.**
   Python-Markdown은 코드블록에서 `"`도 `&quot;`로 바꾼다. 되돌리는 코드에 `&lt;`·`&gt;`·
   `&amp;`만 넣고 `"`를 빠뜨렸다. → `html.unescape`로 교체(한 번만 훑으므로 원문의
   `&lt;`는 그대로 보존된다).

2. **mermaid가 'Syntax error in text'.**
   개행 제거 과정에서 다이어그램 소스가 한 줄로 뭉쳤다. Mermaid는 textContent를 줄 단위로
   파싱한다. `<br>`은 답이 아니다 — textContent에 아무것도 기여하지 않아 줄이 그대로 붙는다.
   → `&#10;`(개행 실체 참조). HTML 소스에는 개행 문자로 존재하지 않아 Blogger의 줄바꿈
   변환에 안 걸리고, 브라우저가 DOM 텍스트로 만들 때는 진짜 개행이 된다.

> **교훈**: 이 프로젝트는 "실제 글을 넣고 눈으로 본다"를 건너뛰면 안 된다.
> 변환 결과가 문법적으로 멀쩡해도 렌더 결과가 깨질 수 있다.
